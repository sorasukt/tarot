# มาตรฐาน UX/UI — sorasukt Tarot

เวอร์ชัน 1.0 · 9 กันยายน 2026

เอกสารนี้กำหนดเกณฑ์ออกแบบและตรวจรับร่วมกันสำหรับหน้าเว็บทุก HTML รวมถึงหน้า “ฉัน” การอ่านไพ่ สมาชิก ไทม์ไลน์ และ Admin เป้าหมายคือใช้งานง่าย เรียบ อ่านสบาย และกู้คืนจากข้อผิดพลาดได้ โดยไม่เสียสิทธิ์เมื่อบริการไม่สำเร็จ

**สถานะ:** เป็นข้อกำหนดสำหรับการพัฒนาและตรวจรับ ไม่ใช่คำรับรองว่าเว็บปัจจุบันผ่าน WCAG แล้วทั้งหมด การเปลี่ยนเอกสารนี้ไม่ได้เปลี่ยนหน้าตาหรือพฤติกรรมบนเว็บจริงโดยอัตโนมัติ

## 1. ฐานอ้างอิงและความหมายของข้อกำหนด

| ฐานอ้างอิง | ใช้กับโครงการอย่างไร |
|---|---|
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | ตั้งเป้าผ่านข้อกำหนดที่เกี่ยวข้องทั้งหมดในระดับ A และ AA; ตารางในเอกสารนี้เป็นจุดตรวจสำคัญ ไม่ใช่รายการครบทุกข้อ |
| [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/) | แนวทางทำ component และ keyboard interaction; ใช้ HTML มาตรฐานก่อนเพิ่ม ARIA; APG เป็นแนวทางประกอบ ไม่ใช่ใบรับรอง |
| [Nielsen’s usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) | ใช้ตรวจความชัดเจนของสถานะ ความสอดคล้อง การควบคุมของผู้ใช้ การป้องกันและแก้ข้อผิดพลาด |
| ข้อกำหนด Tarot ในเอกสารนี้ | ค่า typography, spacing, สี, ขนาดปุ่ม และโครงสร้างหน้าเป็นการตัดสินใจของโครงการ ไม่ใช่ค่าบังคับสากลทั้งหมด |

ข้อกำหนดผลิตภัณฑ์ที่ยืนยันแล้ว: ยังไม่เพิ่ม “แลกสิทธิ์” ในเมนูหลัก; ทางเข้าหลักของไทม์ไลน์อยู่ในหน้า “ฉัน”; ข้อผิดพลาดของผู้ให้บริการหรือระบบต้องไม่ถูกนับเป็นการใช้บริการสำเร็จ

## 2. โครงสร้างและเมนู

- ทุกหน้ามีเป้าหมายหลักที่เข้าใจได้จากหัวข้อและปุ่มหลัก แสดงงานรองเป็นปุ่มรองหรือลิงก์ ไม่ใช้ปุ่มเด่นหลายปุ่มแข่งขันกันในกลุ่มการตัดสินใจเดียว
- รูปแบบหน้าร่วมกัน: header → ชื่อหน้าและคำอธิบายสั้น → งานหลัก/ฟอร์ม → สถานะหรือผลลัพธ์ → footer รายละเอียดเสริมเปิดเมื่อจำเป็น ไม่เพิ่มกรอบซ้อนเพื่อการตกแต่ง
- ชื่อ ลำดับ และปลายทางของเมนูหลักต้องตรงกันทุกหน้าผู้ใช้ ปลายทางที่ระบุในตารางใช้ฐาน `/tarot/`; relative URL ใช้ได้เมื่อ resolve แล้วตรงกัน

| ลำดับเมนูหลัก | ปลายทาง |
|---|---|
| วันนี้ | `/tarot/` |
| เปิดไพ่ | `/tarot/reading/` |
| ดวงดาว | `/tarot/astrology/` |
| ราศี | `/tarot/zodiac/` |
| สีมงคล | `/tarot/colors/` |
| ตัวเลข | `/tarot/numbers/` |
| ตั้งชื่อ | `/tarot/naming/` |
| สมาชิกพิเศษ | `/tarot/membership/` |

- ทางเข้าบัญชีใช้ “ฉัน” เมื่อลงชื่อเข้าใช้ และ “เข้าสู่ระบบ” เมื่อยังไม่ลงชื่อเข้าใช้; การจัดการสมาชิก การเรียกเก็บเงิน และไทม์ไลน์เข้าจากหน้า “ฉัน”
- เก็บ URL `/tarot/history/` เดิมสำหรับลิงก์ตรงและ bookmark; หน้าผลลัพธ์อาจมีลิงก์ตามบริบทไปยังรายการที่บันทึกแล้วได้
- ไม่เพิ่มเมนูแลกสิทธิ์ และไม่ลบ route เดิมเพียงเพื่อซ่อนจาก navigation
- เมนูมือถือเป็น hamburger ที่มีชื่อสำหรับโปรแกรมอ่านหน้าจอ เปิด/ปิดได้ด้วยคีย์บอร์ด และแสดง `aria-expanded`; ไม่ใช้ ARIA `menu` กับ navigation links ปกติโดยไม่จำเป็น
- หน้าปัจจุบันใช้ `aria-current="page"` พร้อมรูปแบบที่ไม่อาศัยสีอย่างเดียว หน้า Admin ใช้ชุดเมนูตามงานผู้ดูแล แต่ใช้กติกาปุ่ม ฟอร์ม สถานะ และการเข้าถึงเดียวกัน

## 3. รูปแบบภาพและค่ากลางของโครงการ

ใช้แนวทาง clean/minimal: พื้นขาว ตัวอักษรเข้ม สีเน้นเท่าที่จำเป็น รายละเอียดตกแต่งต้องไม่แย่งความสนใจจากคำทำนายหรือการกระทำหลัก

| รายการ | ค่าเป้าหมายของ Tarot |
|---|---|
| พื้นและข้อความหลัก | ใช้ `--st-paper` และ `--st-ink` เดิม; ไม่สร้างชุดสีใหม่แยกตามหน้า |
| สีเน้น | ใช้ `--st-accent` เดิมสำหรับจุดเน้นและ focus; สถานะผิดพลาดต้องมีข้อความหรือสัญลักษณ์ร่วมด้วย |
| Font เนื้อหา | ใช้ `--st-font-sans` และ fallback ภาษาไทยเดิม |
| Font หัวข้อ | ใช้ `--st-font-display`; ไม่เพิ่มตระกูลใหม่โดยไม่มีเหตุผลด้านการอ่าน |
| เนื้อหาทั่วไปและช่องกรอก | เริ่มที่ `1rem` (ปกติ 16 CSS px) รองรับขนาดที่ผู้ใช้ตั้งไว้ |
| ข้อความรอง | เริ่มที่ `0.875rem`; ข้อมูลสำคัญ เช่น error และเงื่อนไขการใช้สิทธิ์ไม่ย่อจนอ่านยาก |
| ระยะบรรทัด | เนื้อหาภาษาไทย 1.6–1.8; หัวข้อภาษาไทย 1.25–1.4 และตรวจสระ/วรรณยุกต์ไม่ถูกตัด |
| ลำดับขนาด | H1 ประมาณ 32–48 px, H2 24–32 px, H3 20–24 px ผ่านหน่วยยืดหยุ่น; ไม่บังคับตัดหัวข้อเป็นสองบรรทัดบนทุกจอ |
| Spacing | ใช้ token 4, 8, 12, 16, 20, 24, 32, 40, 48 px เดิม; ใช้ระยะห่างเพื่อแบ่งกลุ่มก่อนเพิ่มเส้นและกรอบ |
| ความกว้าง | เนื้อหาหลักไม่เกิน `--st-content` (1180 px); คำอ่านไม่เกิน `--st-reading` (760 px); ตรวจความยาวบรรทัดภาษาไทยจริงด้วย |
| ขอบจอ | เป้าหมายข้างละ 16 px บนมือถือ และ 24–32 px บนจอใหญ่; ไม่กำหนดด้วยชื่อรุ่นอุปกรณ์ |
| ปุ่มและพื้นที่แตะ | ปุ่มหลักสูงอย่างน้อย 48 CSS px; control แบบแยกชิ้นและปุ่ม icon มี hit area อย่างน้อย 44×44 CSS px ตามมาตรฐานภายในโครงการ |
| ขอบมน | ใช้ `--st-radius-*` เดิมตามประเภท component; ไม่กำหนด radius ใหม่เฉพาะแต่ละกล่อง |
| Motion | สั้นและมีหน้าที่สื่อสถานะ; เคารพ `prefers-reduced-motion`; ไม่บังคับรอ animation เมื่อผลพร้อมแล้ว |

ขนาด 44/48 px เป็นเป้าหมายของโครงการที่เข้มกว่าค่าขั้นต่ำบางกรณีของ WCAG: SC 2.5.8 ระดับ AA ใช้ 24×24 CSS px หรือเข้าเงื่อนไขยกเว้นที่ระบุ เช่น spacing และ inline links ไม่ควรกล่าวว่าทุก target ต่ำกว่า 44 px ผิด WCAG AA ([คำอธิบาย SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html))

## 4. เกณฑ์การเข้าถึงที่ต้องตรวจ

| จุดตรวจ | เกณฑ์รับงาน |
|---|---|
| Text contrast | ข้อความทั่วไป ≥4.5:1; ข้อความขนาดใหญ่ตามนิยาม WCAG ≥3:1 (18 pt ปกติ หรือ 14 pt ตัวหนา) ตรวจคู่สีที่แสดงจริง รวม hover และ error ([SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)) |
| Control contrast | ข้อมูลภาพที่จำเป็นต่อการระบุ control/state ≥3:1 กับสีที่ติดกันตาม SC 1.4.11; เส้นตกแต่งไม่จำเป็นต้องใช้เกณฑ์เดียวกับขอบที่จำเป็นต่อการมองเห็นช่องกรอก ([คำอธิบาย](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)) |
| Keyboard | ทำงานหลักครบโดยไม่ใช้เมาส์ ไม่มี keyboard trap; focus เดินตามลำดับอ่าน ไม่ใช้ positive `tabindex` จัดลำดับแทน DOM |
| Focus | มองเห็นตำแหน่ง focus ชัด และไม่ถูกแถบ sticky/เมนูบังทั้งหมดตาม SC 2.4.11; เป้าหมายโครงการคือไม่บัง control ที่กำลังใช้งาน |
| Screen reader | ชื่อและบทบาทปุ่มถูกต้อง label เชื่อมกับ input, heading เป็นลำดับ, มี `main`/navigation landmarks และทางข้ามเมนูซ้ำ |
| Reflow/zoom | งานหลักยังใช้ได้ที่ความกว้าง 320 CSS px และการขยายข้อความ 200%; ทดสอบ 400% zoom ที่ viewport เดิม 1280 px ด้วย ตารางที่จำเป็นต้องสองมิติเลื่อนเฉพาะส่วนได้ ([reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)) |
| สถานะ | ความคืบหน้าใช้ status/live region แบบสุภาพ; error เร่งด่วนจึงใช้ alert; ไม่อ่านสถานะเดิมซ้ำทุก animation tick ([SC 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)) |
| Dialog | ชื่อ dialog ชัดเจน วาง focus ที่เหมาะสม จำกัด Tab ภายในเมื่อเป็น modal ปิดได้ด้วย Escape และคืน focus ไปปุ่มเปิดหรือจุดถัดไปที่เหมาะสม ([APG dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)) |
| การเลือกไพ่ | เลือก/ยกเลิกด้วยคีย์บอร์ดได้ ประกาศสถานะเลือกและจำนวน เช่น “เลือกแล้ว 3 จาก 5 ใบ”; มีชื่อที่ไม่เปิดเผยหน้าไพ่ก่อนเวลาที่ออกแบบไว้ |
| ฟอร์ม | label มองเห็นเสมอ ไม่ใช้ placeholder แทน label; error ระบุช่องและวิธีแก้ด้วยข้อความ; ไม่ล้างค่าที่ถูกต้อง |
| การลงชื่อเข้าใช้ | อนุญาต paste และ password manager; ไม่เพิ่มแบบทดสอบความจำเป็นเงื่อนไขโดยไม่มีทางเลือกที่เข้าถึงได้ ตรวจช่วงส่งต่อและกลับจากผู้ให้บริการด้วย |

## 5. สถานะของคำทำนายและเสียง

ทุกงานที่เรียกเครือข่ายต้องออกแบบอย่างน้อย: พร้อมใช้ → กำลังทำงาน → สำเร็จ / ไม่สำเร็จ; กรณีผลว่าง ไม่มีสิทธิ์ รอยืนยัน และออฟไลน์ต้องแยกจากกัน

| สถานการณ์ | สิ่งที่ผู้ใช้เห็นและทำต่อได้ | หลักการนับสิทธิ์ |
|---|---|---|
| ก่อนเริ่ม | คำอธิบายสั้น ปุ่มบอกการกระทำ; แสดงยอดคงเหลือเมื่อมีข้อมูลยืนยันจากระบบ | ไม่ลดตัวเลขล่วงหน้า |
| รอคำทำนาย | “กำลังเตรียมคำทำนาย…” พร้อมสถานะรอ; ป้องกัน submit ซ้ำ เก็บคำถามและไพ่เดิม | การส่งคำขอไม่ใช่การใช้งานสำเร็จ |
| นานกว่าปกติ | “ใช้เวลานานกว่าปกติ กำลังลองให้อีกครั้ง” เมื่อมีการลองใหม่จริง; ไม่สร้างเปอร์เซ็นต์หรือเวลานับถอยหลังปลอม | retry รายการเดิมต้องไม่หักซ้ำ |
| สร้างผลไม่ได้ | “ยังสร้างคำทำนายไม่สำเร็จ ครั้งนี้ไม่ใช้สิทธิ์” พร้อม “ลองไพ่ชุดเดิมอีกครั้ง” เมื่อระบบยืนยันเงื่อนไขนี้ได้ | ไม่หักเมื่อผู้ให้บริการหรือระบบล้มเหลว |
| ขาดการเชื่อมต่อ | คงคำถาม/ไพ่และบอกว่ารับผลไม่สำเร็จ; ถ้ายังตรวจยอดไม่ได้ให้บอกว่ากำลังตรวจ ไม่แสดงยอดที่คาดเดา | ไม่ถือว่า HTTP response ฝั่ง server เป็นหลักฐานว่าผู้ใช้ได้รับผล |
| แสดงผลสำเร็จ | แสดงคำอ่านครบและแจ้งผลการบันทึกตามจริง; ความล้มเหลวของ analytics/การยืนยันยอดต้องไม่ซ่อนคำอ่าน | ยืนยันรับผลแล้วจึงบันทึกยอดใช้ |
| เสียง | ปุ่มฟัง/หยุดและสถานะ; ไม่มี autoplay; ถ้าเปิดเสียงสำรองให้แจ้งสั้น ๆ | เสียงล้มเหลวหรือสำรองจากอุปกรณ์ไม่หัก; แนวทางที่กำหนดล่าสุดนับเมื่อเสียงผู้ให้บริการเล่นจบ |
| รอยืนยันรายการก่อน | แจ้งว่ามีรายการค้างชั่วคราว ไม่ใช้ข้อความว่า “ใช้ครบแล้ว” | การจองชั่วคราวที่หมดอายุต้องไม่แปลงเป็นยอดใช้ |
| สิทธิ์ครบจริง | แจ้งยอดที่ยืนยันและเวลารอบใหม่ตามเวลาไทย; ทางเลือกสมาชิกเป็นปุ่มรอง | ไม่ปะปนกับ timeout หรือบริการขัดข้อง |

กติกาการยืนยันรับผลอยู่ใน PR #25 และ [เอกสารการนับสิทธิ์](reading-quota-fix.md) ต้องตรวจสถานะการนำขึ้นระบบก่อนใช้ข้อความรับรองผู้ใช้ การมีข้อกำหนดนี้ไม่แปลว่า release ปัจจุบันนำไปใช้แล้ว

ข้อผิดพลาดต้องบอกปัญหาและทางออกโดยไม่โทษผู้ใช้ ไม่แสดงชื่อโมเดล API หรือ stack trace ในหน้าทั่วไป ปุ่มสนับสนุนหรือซื้อสมาชิกต้องไม่แย่งความเด่นจากการแก้ข้อผิดพลาด และไม่สื่อว่าการจ่ายเงินจะแก้เหตุขัดข้องของระบบ

## 6. Component และเนื้อหา

| Component | ข้อกำหนดร่วม |
|---|---|
| Button/link | ใช้ `<button>` สำหรับการกระทำ และ `<a>` สำหรับเปลี่ยนหน้า; ปุ่ม icon ต้องมี accessible name; งานสำคัญใช้ข้อความกำกับที่มองเห็น |
| Form | ใช้ชนิด input/autocomplete ที่เหมาะสม; ตรวจข้อมูลข้างช่อง หลัง submit ผิดให้เข้าถึงสรุปข้อผิดพลาด/ช่องแรกได้; ไม่เปลี่ยนหน้าทันทีที่เลือกค่าโดยไม่คาดหมาย |
| Result | มีหัวข้อ ภาพรวม และรายละเอียดแบ่งส่วน; ลำดับอ่านตรงกับภาพ; คำอ่านเดิมไม่หายเพราะการโหลดข้อมูลประกอบล้มเหลว |
| Empty state | บอกว่าทำไมยังไม่มีข้อมูลและมีทางเริ่ม เช่น “ยังไม่มีคำอ่านที่บันทึกไว้” + “เปิดไพ่” |
| Payment | แสดงราคา สกุลเงิน รอบชำระ การต่ออายุ และผลของการเปลี่ยน/ยกเลิกก่อนยืนยัน; ห้ามแสดงสำเร็จเพียงเพราะกลับจากหน้าชำระเงิน |
| Destructive action | ลบข้อมูล/คืนเงิน/เปลี่ยนสิทธิ์ใน Admin ต้องระบุรายการและผลกระทบชัดเจน พร้อมทางยกเลิก; ไม่เพิ่ม confirmation ให้ทุกคลิกทั่วไป |
| Consent | แยกการยอมรับนโยบายจากการสมัครสมาชิก; เปิดอ่านนโยบายได้และออกจากขั้นตอนที่ยังไม่ยอมรับได้ โดยไม่บันทึกว่าผู้ใช้ยอมรับ |
| ภาษา | ไทยธรรมดา คำเดียวกันตลอดระบบ; วันที่และรอบสิทธิ์ระบุเวลาไทยเมื่อมีผลต่อการตัดสินใจ; ชื่อผู้ให้บริการอยู่เฉพาะบริบทที่จำเป็น |

## 7. ตำแหน่งไฟล์และสิ่งที่ต้องปรับตามลำดับ

ใช้ `assets/css/core/design-system.css` เป็นค่ากลาง, `core/` สำหรับกติกาทั่วไป, `components/` สำหรับส่วนใช้ซ้ำ และ `pages/` สำหรับหน้าเฉพาะ ตาม [โครงสร้าง CSS](../assets/css/README.md) ไม่แก้ปัญหาความสอดคล้องด้วยการต่อ override ใน root CSS ไปเรื่อย ๆ

สิ่งต่อไปนี้ตรวจจากค่าต้นฉบับ เป็นรายการต้องทวนเมื่อปรับ UI ไม่ใช่ผลทดสอบ computed style ทุกหน้า:

| สิ่งที่พบ | การใช้งานตามมาตรฐานใหม่นี้ |
|---|---|
| `--st-subtle: #8a8a8a` บนขาวมี contrast ประมาณ 3.45:1 | ไม่ใช้กับข้อความทั่วไปที่ต้องผ่าน 4.5:1 |
| `--st-line-strong: #c8c8c8` บนขาวประมาณ 1.67:1 | ทวนขอบช่องกรอกเมื่อเป็นสิ่งจำเป็นเพียงอย่างเดียวที่ระบุ control; ใช้เส้นตกแต่งได้ตามบริบท |
| `--st-muted: #6f6f6f` บนขาวประมาณ 5.02:1 | ใช้กับข้อความรองได้ในคู่สีนี้; ต้องตรวจใหม่เมื่อพื้นหรือ opacity เปลี่ยน |
| หัวข้อร่วมมี `line-height: .96` | แยก line-height ภาษาไทยตามข้อ 3 และตรวจหลายบรรทัดกับสระ/วรรณยุกต์จริง |
| `--st-page-gutter` เดิมถูกหักจากความกว้างรวม | ค่ารวม 24 px เท่ากับขอบข้างละ 12 px; ต้องแยกความหมายให้ชัดก่อนปรับเป็นเป้าหมายข้างละ 16 px |

## 8. เกณฑ์ก่อนรับงาน UX/UI

- มีหลักฐานของหน้าหรือ component ที่เปลี่ยนในจอ 320, 390, 768 และ 1440 CSS px ตามความเหมาะสม พร้อม zoom/reflow และคำไทยยาว
- ทดสอบคีย์บอร์ดครบงานหลัก และอย่างน้อย VoiceOver + Safari กับ NVDA + Chrome ในรอบ release ที่เปลี่ยน interaction สำคัญ; ทวน Android/TalkBack สำหรับ flow มือถือที่เปลี่ยน
- ตรวจ contrast ทุก state ที่เปลี่ยน และใช้ automated accessibility scan ประกอบการตรวจด้วยคน; ผล scan ผ่านไม่ใช่หลักฐานว่า WCAG ผ่านทั้งหมด
- มีกรณี loading, error, empty, success, offline, retry และสิทธิ์ครบสำหรับ flow ที่เกี่ยวข้อง; ไม่มีข้อมูลหรือสิทธิ์หายเมื่อจำลอง network failure
- เมนูตรงตามข้อ 2, ไม่มี duplicate ID, ลิงก์และ asset ของหน้าที่แก้ไม่เสีย และ browser console ไม่มี error ที่เกิดจากการเปลี่ยนนี้
- ทดสอบใช้งานกับคนที่ไม่ได้พัฒนา flow โดยให้งาน “เลือกไพ่และรับคำทำนาย”, “ลองใหม่หลังเครือข่ายขัดข้อง”, “หาไทม์ไลน์ในฉัน”, “ฟัง/หยุดเสียง” ตามขอบเขตงาน บันทึกสำเร็จ/ติดขัด เวลา และความเข้าใจเรื่องสิทธิ์ แล้วเปรียบเทียบก่อน–หลัง ไม่ตั้งตัวเลขความสำเร็จปลอม
- บันทึกสิ่งที่ผ่าน สิ่งที่ยังไม่ได้ทดสอบ และข้อจำกัดจริงใน PR; งานเอกสารอย่างเดียวระบุ N/A ได้ ไม่อ้างว่าได้ทดสอบ UI แล้ว
